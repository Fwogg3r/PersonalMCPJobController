# Design review: Spotify connector flags (2026-11-10)

Reviewer: Opus (plan subagent, read-only). Outcome recorded in [DECISIONS.md](../DECISIONS.md) under "Spotify connector".

## Position put to the reviewer

The connector is native, uses OAuth PKCE and covers every feature. The owner chose `auto_clean` for playback. The proposal:
- Reads are `untrusted_output` (catalog names are third-party text), and `spotify_devices` is not.
- `spotify_search` is `egress`.
- Playback acts are `auto_clean` with ids only.
- `spotify_queue` / `spotify_play` accept either URIs or free text in one tool (`egress`).
- Saving and unsaving is `ask`.
- Adding to and removing from a playlist is `ask`, and it was an open question whether it should be egress.
- `spotify_playlist_create` is `ask` + `egress`.

Questions:
1. Should queue/play mix URIs and text in one tool, or be split?
2. Is a Spotify search query really egress?
3. Should playlist writes be egress?
4. What is missing?

## Reviewer's answer (summary)

- **Split queue/play.** The egress check in `executor.call_tool` runs before the act block and returns a flat `Denied`, with no approval path. Almost every Spotify run reads track names first, so a combined egress tool would be useless after the first read. URI-only tools should be non-egress and usable with approval when the run is tainted. The by-name variants keep the one-call "queue Song X" for clean runs.
- **Keep search as egress.** The repo applies "model-chosen arguments leave the machine" even to `weather_forecast` and `places_*`. Spotify reads also mark the run `sensitive`, so a query could carry listening history out. Relax it later only with a documented owner override.
- **Make playlist add/remove egress.** Public and collaborative playlists are readable by others, and the track choice can encode bits.
- **Treat device names as untrusted.** Friends' Connect speakers and Jam sessions show up in the device list.
- **Act-ledger repeat.** A second `spotify_pause()` in a thread has the same payload hash and asks again. Idempotent playback needs a `repeatable` flag.
- **Missing:**
  - bound volume (with an optional `max_volume`) and seek;
  - validate URIs with a strict regex, and allow album/playlist/artist URIs only as a play context;
  - cap list sizes;
  - request the smallest scopes, with `playlist-modify-public` only behind an option;
  - give clear Premium errors;
  - return no third-party text from playback acts.

## What was built

The reviewer's table was adopted, with these deviations:
- `spotify_queue_search` and `spotify_search` take up to 5 queries per call, and `spotify_play_search` takes one.
- Save and unsave take any `spotify:` URI (max 20).
- `spotify_queue` and `spotify_play` by URI are also `repeatable`.
- Seek is bounded at 0 only, because Spotify itself skips past the end of the track.
