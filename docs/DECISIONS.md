# Decisions

Design decisions and the reasoning behind them, newest first. Details of how each works are in [ARCHITECTURE.md](ARCHITECTURE.md).

## Generic connectors for everyday tools; automating repeated requests
- **`kind: command` YAML connectors** turn any command-line tool into pmjc tools without Python.
  - They run as argv, never through a shell.
  - Every parameter is checked against a `pattern` or `choices`, and values starting with `-` are refused.
  - The files are read from disk only, never created or edited through the API.
- **Built-in `files`, `pc`, `ssh` and `lmstudio` connectors** cover most "my own machines" needs.
  - **SSH** describes any machine by address, user, port, key, jump host or proxy command, or reuses a `~/.ssh/config` alias. It never sends passwords, and refuses values that SSH would read as options.
- **Automation is offered, never assumed.** pmjc remembers requests, groups repeated ones, and turns one into a job with a click. Such jobs notify only when there's something new. Auto-approval is an explicit per-tool list and never applies to runs that have read third-party content.
- **Home Assistant service calls need an explicit target** and honour `blocked_entities` and `blocked_patterns`, so devices that must never switch off (like a server's power socket) stay protected.

## Remote access: in-app auth instead of a login proxy
- **The obvious setup breaks claude.ai.** Putting a browser-login proxy in front of `/mcp` (e.g. a Cloudflare Access app) stops claude.ai and the mobile apps from connecting, because they can't complete a browser login.
- **So pmjc authenticates by itself:**
  - OAuth 2.1 through FastMCP with Google or GitHub, limited to an explicit identity allowlist (verified email required), for Claude's connectors;
  - scoped bearer tokens for Shortcuts, scripts and other CLIs.

  The server binds to localhost, and any tunnel can publish it.
- **Considered:** Cloudflare's managed MCP OAuth / MCP portals, which tie the setup to one provider, and a custom OAuth Worker, which is more code to own. Either can still sit in front, but neither is required.

## Watches: temporary monitors for one request
- **The request flow:**
  1. check what's connected;
  2. answer now if possible;
  3. otherwise start one watch (time, event or poll);
  4. it fires once, answers, delivers, and ends.
- **Watches are separate from jobs.** Jobs are recurring and owner-defined. Watches run even with background monitoring and scheduled jobs off, because the request itself authorizes them, and they turn off any source they started.
- **The model is the orchestrator,** guided by tool descriptions and server instructions. pmjc has no rule-based planner.
- **One process owns the scheduler.** Others (stdio MCP, CLI) write watches to the database, and the service adopts them every 5 s.

## Nothing in the background by default
- Background monitoring (per source), scheduled jobs and local-model auto-start all start **off**. With auto-start off, a local host counts only if the model is already loaded, so on-demand loading can't fill a GPU unasked.
- **The data folder on Windows is `%USERPROFILE%\.pmjc`, not AppData.** MSIX-packaged apps (such as the Claude desktop app) redirect the AppData writes of processes they start into a private copy, so a CLI started from them and a service started by Task Scheduler would otherwise see different folders.

## Security model (from an external review)
- **Fail-closed tool tags:** `@tool` defaults to `act`, and tools declare `untrusted_output` and `egress`.
- **Taint is derived:** after a run reads third-party content, egress tools are blocked and every action needs approval.
- **Approval on every agent interface,** stdio included. Approvals are tied to a payload hash, single use, and expire. Opening a link only shows the request; approving takes a POST.
- **`claude -p` is locked down:** its own config folder, no built-in tools, only pmjc over MCP, and no API keys in its environment.
- **Requests are checked:** Host allowlist and Origin check; nothing is trusted because of the source IP.
- **Secrets are encrypted** with an envelope key held in the OS keyring and redacted from logs.
- **Third-party plugin packages** load only when the user enables them.

## PC-native sensing
- **Notifications are read from the PC's notification center** through the WinRT `UserNotificationListener`, which works from unpackaged Python on Windows 11. The rejected alternatives:
  - a separate always-on phone;
  - Phone Link mirroring, which uses Bluetooth and stops when the phone leaves;
  - iOS, which has no API for reading other apps' notifications.
- Banners can be hidden per app, so only pmjc sees them.

## Modular core
- **One registry feeds every interface:** MCP, REST/OpenAPI, CLI, dashboard and tool-schema exports.
- **A connector is one Python class or one YAML file.**
- **Personal data never enters the repo:** settings, credentials, jobs and browser profiles live in `PMJC_HOME`.
- **Model routing is an ordered, user-configurable list:** local first, then Claude Code on the user's plan, then paid APIs with budgets. A run stays on one provider, and `private` jobs stay local.

## Cross-session context
- **Problem:** sessions are stateless and come from different vendors, but a request (a watch that fires later, a message waiting for a reply) outlives them.
- **Decision:** pmjc keeps the shared state: threads, notes, contacts and a user-editable `model.md`. Context reaches a model four ways, because no single one is reliable across clients: server instructions, a header on the first tool result of each MCP session, the `pmjc_context` tool, and the system prompt of pmjc's own runs. The first two work even if the model never calls `pmjc_context`.
- **Trust tiers instead of "tainted can't write".** Blocking writes from tainted sessions isn't enough: a clean agent can still be fed a poisoned value. So every item carries owner/agent/untrusted provenance; models are given owner text verbatim, agent text labelled and untrusted text never (only metadata); agents can't overwrite owner notes; agent-proposed contacts need the user's approval (a contact handle ends up in a deep link).
- **Act ledger.** The failure that matters when a session resumes is repeating a side effect. Recording tool + payload hash per thread, and asking for approval again on a repeat, is cheap and independent of the model's judgment.
- **Handoff over delegation.** When pmjc can't act as the user, it notifies them with a one-tap link rather than driving a more capable local agent. Delegation (`pmjc_delegate`) widens the attack surface (a second agent with browser control) and is deferred until it has its own threat model.
- **Limits live next to the tools.** `limitations` and `native_alternatives` are appended to each tool's description, so a blank session sees them in the tool list; `pmjc_capabilities` adds the task-level routes and drops the native and workaround routes for tainted sessions, so third-party text can't steer a model toward them.
- **Retention.** Closed threads are deleted after 90 days (`thread_retention_days`); `private` on a thread is sticky and keeps its asks on local models.

## Discord front door
- **Problem:** reach pmjc from any device without a tunnel, OAuth or a custom app, with push replies when watches and jobs finish.
- **Decision:** the service connects to the Discord gateway with the user's own bot and routes the owner's messages through `ask()`. Considered instead: a long-running Claude Code session with a Discord channel plugin (more capable, but it uses the plan for every message, stalls on permission prompts when unattended, and bypasses pmjc's scopes and approvals), and only the claude.ai connector (no push).
- **A small gateway client on `websockets` instead of discord.py:** the door needs identify, heartbeat, resume, messages and button clicks, about 100 lines with no new dependency. Revisit if it needs voice or sharding.
- **The owner's Discord id is the identity.** Messages from anyone else are never read. Runs are ordinary remote callers, so act tools still need approval; the approval is a button click checked against the owner id in the interaction, which the model can't produce.
- **Continuity:** `ask()` takes `history_turns`, so the last exchanges of the pmjc thread go back into the prompt. Third-party items in that history taint the run, as reading them through a tool would.
- **Slash commands as guild commands; `/tool` bypasses the model but not approvals.** Registered per server on connect (instant, unlike global commands), owner id checked on every interaction. `/tool` calls `executor.call_tool` as the door caller, so scopes, taint rules and Approve/Deny buttons apply unchanged. The per-call trace uses an `on_tool` hook on `Caller` that sees only name, args and status.

## Local model context size (24 GB GPU)
The numbers below are one example setup (a 27B 4-bit model on a 24 GB card); keep the method and re-measure on your own hardware.
- **Decision:** run the local model (Qwen3.8-27B, 4-bit, about 16.5 GB of weights) at a **64k** context instead of 32k. Set it with the provider's `context_tokens` in settings; pmjc loads LM Studio models with that `--context-length`.
- **Why:** measured on an RTX 3090 (24 GB, with a normal desktop's apps also on the GPU). 64k cost about 1 GB more GPU memory than 32k (21.7 -> 22.7 GB) at nearly the same speed (59.9 -> 56.7 tokens/s on a short prompt; first token 0.34 -> 0.79 s). It's cheap because the model's attention is hybrid: only 16 of its 64 layers keep a cache that grows with context. Twice the room for tool loops and history at no real cost.
- **Going higher doesn't pay:** at 96k the card fills (24.1 GB) and Windows spills 1.4 GB into system RAM, which the GPU reaches far more slowly: **17.8 tokens/s**. At 128k, 3.7 GB spills: **13.1 tokens/s**. Windows doesn't refuse an oversized load; it gets slow instead, so check spill (Task Manager: GPU "Shared memory", or the `GPU Adapter Memory` counters) and not only whether it loaded.
- **Headroom:** keep at least 1-1.5 GB of GPU memory free for other apps (browser, chat apps, screen recorders), whose use goes up and down; if they push the total over the card's size, the model spills partway through a reply. 64k leaves about 1.9 GB; 80k would sit at the edge.
- **If more context is ever needed:** (1) 8-bit KV cache in LM Studio's load settings roughly halves the per-token cost, maybe ~96k with the same headroom and a small quality risk (untested); (2) send small-context models only the relevant tool schemas, which frees fixed overhead (roadmap: auto-condense); (3) condense long runs (same entry); (4) close GPU-heavy apps (a few hundred MB, not reliable). Re-measure with the same steps (load at the size, check dedicated and shared GPU memory, time a short reply) after model or driver changes.

## Approval outcomes and the shell-command fallback (owner, 2026-11-08)
- **Where a follow-up goes after an approval decided outside Discord:** a note in the thread (unread) and a message to the notify channels, controlled by `approval_outcome_notify` (default true). Considered instead: a thread note only.
- **Does an approved action's result taint the run? Per tool.** It taints only if the tool is marked `untrusted_output` (it can return third-party text). Plain confirmations stay trusted, so the follow-up can still act normally. An unknown tool taints, to be safe. Considered instead: always taint (safest, but every follow-up send needs approval again) and never taint (a result echoing third-party text could steer the run).
- **Shell-command fallback (phase4/j), who may propose:** set by a config option. The public default is owner chats only (Discord DM, REST, CLI runs the owner started, never tainted). Jobs and watches can be allowed through config.
- **Who counts as the owner for proposals (owner, 2026-11-09):** any authenticated caller that is not a job or watch run: Discord DM, REST, CLI and MCP clients (local, remote-token or OAuth). pmjc can't tell the owner's remote MCP client from an agent the owner runs, and every authenticated route is the owner's own. Approval is still required for every command.
- **Shell-command limits:** a timeout and an output cap, both set in config. The model may ask for a different timeout or cap in the request, shown to the owner in the approval. The full command is always shown and logged, and it runs only after approval.
- **Public by default:** the repo ships generic, publicly usable defaults. Settings specific to the owner (configs, their bots and so on) go in the owner's private dev-tools repo, not here.

## Taint hardening: writers, defanged links, sensitive flag (phase4/ab, 2026-11-09)
- **Writers go through approval after taint.** `@tool(..., writes_state=True)` marks tools that write state later runs trust: `pmjc_memory_set`, `pmjc_memory_delete`, `pmjc_contact_set`, `pmjc_job_create`, `pmjc_job_delete`, `pmjc_watch_start`. The executor turns a call from a tainted run into an approval request (auto-approve doesn't apply). New tools opt in; mounted MCP tools stay `act`. Considered instead: refusing the call (the old memory/contact behaviour) and approving only some. Refusing leaves the model stuck and still left jobs and watches open; approval keeps the owner in the loop.
- **An approved write is still untrusted.** The approval row records that the requester was tainted; on approval the tool runs as a tainted read-scope caller, so notes and threads get the `untrusted` label (never shown verbatim to models), a contact stays a proposal, a job loses `actions` scope and a watch is read-only. `pmjc_thread_start` and `pmjc_thread_note` are not flagged: from a tainted run they already store untrusted items.
- **Link defang format** (answers, job and watch results, approval previews, only for tainted runs): `https://host.example/p?q=x#f` becomes `` `hxxps://host[.]example/p` ``: scheme `hxxp(s)`, host dots `[.]`, no userinfo, query or fragment, in a code span (no code span inside code blocks or JSON). Chosen because it is readable, can't be linkified or unfurled by a client (a bare domain would be), and re-defanging is a no-op. Trusted hosts keep normal links: `output_link_allowlist` in settings (empty by default) plus hosts of URLs the run's tools returned; a query string survives only when that exact URL appeared in a tool result, and URLs the model chose after taint never count. Considered instead: angle brackets (Discord still fetches the link on some clients) and dropping links entirely (loses useful results).
- **Embeds:** Discord answers from tainted runs carry flag 4 (SUPPRESS_EMBEDS), approval messages always do, and the Discord notification path always does (it carries job, watch and approval text). The dashboard inserts answers as text and its CSP allows only same-origin and data images.
- **Declared reads tightened:** `read_sites` matches only URLs without a query string, `read_urls` match exactly, and the new `read_prefixes` match scheme + host + path prefix on a path-segment boundary (no `..`, no query unless the prefix has one). The path under `read_sites` is still model-chosen, so prefer `read_prefixes` or `read_urls` for untrusted jobs.
- **`sensitive`:** derived and fail-closed, set at the start by the system block (model.md, notes), thread history and approval-result text, and by any tool with `private_output=True` (the default). `private_output=False` only on public-web tools: web_search, web_fetch, craigslist_search, ebay_search, weather_forecast, places_nearby, places_geocode. Browser reads (browser_read/extract/browse) stay private: they use the owner's signed-in browser profile, and its default sites include messaging, so a page can be the owner's private messages (changed in review, 2026-11-09). No behaviour depends on it yet.

## Declared browser reads (phase4/s)
- **Problem:** `browser_read` is `egress` (the URL leaves the machine), so after one page of untrusted content a run can't read a second one.
- **Decision:** a job file or watch spec may declare `read_urls` (exact URLs) and/or `read_sites` (domains, subdomains included). The executor lets `browser_read` and `browser_extract` through after taint when the `url` argument matches that list, because the owner fixed the URL, not the model. Everything else keeps the egress rule. The browser connector's `allowed_domains` check still applies on top.
- **Who can set it:** only the owner. The lists live in the stored definition and are loaded into the `Caller` by the job engine or watch runner; there is no tool argument for them. `save_job` clears them for any non-admin creator and `watches.start` drops them from specs from non-admin callers, so a model (tainted or not) can't grant itself reads.
- **Residual risk:** `read_sites` lets a tainted run choose the path on that site (since phase4/ab never a query string), which could still carry data out in the URL path. Prefer `read_prefixes` or `read_urls` for untrusted jobs and reserve `read_sites` for sites the owner trusts not to log hostile requests.

## Tool selection for small-context models (phase4/w, 2026-11-09)
- **Options:** (a) deferred loading via a new `pmjc_tools_load` meta-tool; (b) keyword pre-selection only; (c) a first-pass model call to pick connectors; (d) compact schemas, then a fixed per-run toolset picked before turn 1.
- **Decision:** (d) first, after an external design review. Step 1: a provider option `schema_mode: full | compact` (default `full`); compact sends first-paragraph docs, no per-property titles, flattened nullable types, and connector limits once (not repeated per tool, no client-only advice). Measure the saving before building more. Step 2, only if still needed: core tools plus default connectors always, optional connectors chosen before turn 1 by alias/tag match on the request and *trusted* thread turns, plus the thread's previously used set (sticky per thread); `pmjc_capabilities(task)` doubles as the loader (no new meta-tool); a call to an unsent tool that exists, is allowed for the run and validates simply executes; a token budget on loading; no egress connectors offered after taint; deterministic tool order so the local model's prompt cache keeps working.
- **Why:** a loader tool costs extra turns, invalidates the local KV cache each time the tool list changes, and relies on small models noticing they lack a tool, which they do badly (they say "I can't" or invent a name). Shrinking schemas has no behavioural risk. Loading a schema never grants anything: scopes, the run's `tools` allowlist (`Caller.allowed_tools`, enforced in the executor), taint and approvals are all checked at call time.

## Mounting existing MCP servers (phase4/b)
- **Decision:** `mcp_servers:` in settings.yaml mounts servers (stdio argv or streamable HTTP) as connectors; their tools are named `<id>__<tool>` and run through the executor like any other tool. Considered instead: a bridge that exposes the server to the model directly (would bypass scopes, taint and approvals).
- **Safe defaults for a mounted tool:** scope `act` (approval needed) unless the server marks it `readOnlyHint: true`, then `read`; `untrusted_output=True` and `egress=True` always. An unknown server can return anything and may send arguments anywhere, so only the owner's per-tool `overrides` in settings.yaml relax this. The hint is the server's own claim, so a malicious server could mark a write as read-only; mount only servers you trust, and use `overrides` or `tools`/`exclude` to tighten.
- **Who can change it:** only settings.yaml. The command, args and url are never settable through the API (the settings and connector-credential endpoints don't accept them). Secrets come from the credential store by name (`mcp.<id>.<NAME>` for `env`, `mcp.<id>.bearer` or `bearer_credential` for HTTP), never inline. A stdio server gets only those names plus a minimal default environment, not pmjc's own environment.
- **Not yet:** images and other binary results are replaced by an "omitted" note; OpenAPI import is still open.

## Multi-step work on local models: research sub-runs first, task runner later (phase4/y, phase4/p, 2026-11-09)
- **Options:** (a) a general task runner (plan on the thread, one fresh run per step) plus in-run condensing; (b) only condense one long run; (c) a Claude planner with local executors; (d) a quarantined research sub-run exposed as a tool, plus bounded results and condensing, with the runner as a later layer. Reviewed by Opus.
- **Decision:** (d), in this order. (1) Close laundering holes: memory, contact, job and watch writers need approval after untrusted content; declared reads match exact URLs or path prefixes, with no model-chosen query strings. (2) Defang output egress for tainted runs: links outside an allowlist are rewritten in answers and approval previews, Discord embeds are suppressed, and the dashboard renders no remote images. (3) A derived, fail-closed `sensitive` flag next to `untrusted`: read tools default to private output and web tools are not; model.md, memory, history and approval details count as sensitive. (4) `pmjc_research(question)`: a sub-run with only web tools and a stripped prompt (not sensitive, so search -> fetch -> fetch works), returning a capped untrusted summary plus sources. (5) Bounded context: result caps per provider with paging handles (`pmjc_result_get`), a tool-less condense pass at about 70% of context that keeps the flags, and summaries written back to the thread. (6) An escalation card that lists size, cost and the classes of data that would leave. (7) The task runner only if real multi-step needs remain: a frozen plan from trusted input, per-step tool sets that are research or private but never both, typed outputs between steps, and status-only updates from tainted steps.
- **Why:** research and context bloat are separate problems with smaller fixes than a runner. A plan the model can edit after reading untrusted content gives injected text control of the task (control flow must come from trusted input only). A `sensitive` flag only helps if it is derived rather than declared, because every ask carries model.md. And the rendered answer is itself a way out (link unfurls), so it needs defanging.
- **Quarantine rule (step 4, built):** egress after untrusted content is allowed for exactly one kind of caller, the research sub-run (`Caller.quarantine`), and only while its `sensitive` flag is False. The flag is a plain dataclass field set in one place (`research.new_caller`); jobs, watches, tokens, OAuth, REST and MCP build callers from explicit fields and never read it, and a test scans the source so no other module can set it. The sub-run holds nothing private: tools limited to the public web tools in `research.tools` (any tool with private output, state writes or non-read scope is dropped), a fixed prompt without model.md, notes or thread history, and a question capped at 300 characters that is always audited. If a private-output tool ever ran inside it, `sensitive` would flip and the normal egress rule would apply again (its own result paging is exempt: it only reads the run's own results). The parent is denied `pmjc_research` once tainted, becomes tainted by the call (the summary is untrusted), and stays non-sensitive only if it already was. Sources are the pages the sub-run fetched plus cited URLs that appeared in a tool result; other URLs in the summary are defanged. Residual risk: the question and the fetched URLs are model-chosen and leave the machine, but the sub-run has nothing private to put in them; the parent's own question is the only channel, which is why the tool tells models to keep it self-contained and free of private details.

## Front-door routing: rules first, a model triage call only if the data shows it helps (2026-11-09)
- **Goal (owner):** one chat interface (any OpenAI-compatible app on PC or phone, through `/v1`) that picks the model and the tools for each request, sending short briefs and loading full tool schemas only when needed.
- **Options:** (a) an LLM triage call on the loaded local model before each request (tier + connectors as JSON); (b) deterministic constraints and owner rules, with a sticky provider per thread and user-driven escalation; (c) a dedicated small classifier model; (d) an embedding router over past requests. Reviewed by Opus.
- **Decision:** (b) first. Hard constraints come first: private means local only, images go to a vision provider, a large context goes to a big-context provider, a busy GPU goes to the cloud. Then owner `route_rules` (prefix, keyword, surface), first match wins, mapping to named ordered `tiers` (`default`, `strong`, `local`; the order is the fallback). The provider chosen on a thread's first turn sticks for that thread. Every decision is logged, and "/strong"-style retries are recorded as misroute labels. Answers carry a footer (model, rule, tools, cost), stripped from incoming history. Tools are chosen by phase4/w step 2: briefs for the rest, loading on demand. Next: user-driven escalation, then an executor-enforced act ledger so a run can switch provider mid-run without repeating acts, then a model-invoked `pmjc_escalate` (local runs, daily cap, approval when tainted, sensitive or paid; never for private threads). A triage call only if the eval suite on logged retries shows it beats the rules, using grammar-constrained JSON on turn 1 only, clamped to the candidate set.
- **Why:** a triage call on the same local model evicts LM Studio's prompt cache (the real run then re-reads everything), judges its own limits as badly as the main run would, and duplicates the tool selector. Rules add no latency, are explainable and can't be steered by injected text, and the retry log gives labelled data to test triage against. Invariant: routing only chooses within the filtered candidate set, never widens it, and an escalation card lists the destination, payload size, untrusted sources, sensitive data classes and cost.
- **Router fixes found in review:** `gpu_busy` must ignore LM Studio's own inference; interactive requests must not block on starting a local host (`healthy(start=False)`, start in the background, route elsewhere for now).
- **Revision, owner decision 2026-11-09 (GPU busy, sticky provider):**
  - *GPU busy no longer routes to the cloud silently.* LM Studio is a compute app and a game is a graphics app, so `nvidia-smi --query-compute-apps` can't tell a gaming PC from an idle one. Busy now means: a process in `router.gpu_busy_processes` (default empty, the owner lists games or launchers) is running; or utilization is at or over the threshold while pmjc has no local request in flight. High utilization while pmjc has one in flight is not busy, because pmjc can't tell its own load from a game and trusts only the process list.
  - *When the plan wanted a guarded local provider and the GPU is busy*, an interactive request does not run. It returns a notice naming what uses the GPU and offers: use local anyway (an approval of the internal `pmjc_route_override`, since it competes with the owner's game), use a cloud model (only if the thread isn't private and a cloud candidate exists), or wait (do nothing). Choosing runs the original request in the same thread through the approvals continuation, and the choice is written to the routing log. `router.gpu_busy_action: ask | cloud | local` (default `ask`) lets people who don't game turn the prompt off; private work never goes to the cloud. Jobs and watches use `router.gpu_busy_jobs: wait | cloud | local` (default `wait`): a job run is recorded as `deferred` and the next schedule or event retries it, a watch retries after `gpu_busy_backoff_seconds` up to `gpu_busy_max_waits` times. Chosen over an in-process retry loop for jobs because the next schedule is already a retry and holds no worker.
  - *Sticky provider remembers both the planned and the actual provider* (plus whether it was a fallback and why). A fallback is not a preference. Next turn, if the planned provider is available again: stay on the fallback when the thread is "hard" (the plan's tier was `strong`, the last run made at least `router.stay_tool_calls` tool calls, the history was condensed, or the history is over `router.stay_history_share` of the planned provider's context), because switching costs context and quality; otherwise switch back. The footer says which happened and offers the pivot (`reply /local to switch back`, `/strong to stay on the cloud`; a prefix replaces the sticky choice), and the routing log records the stay or switch with its reason. A private thread never sticks to a non-local provider.
